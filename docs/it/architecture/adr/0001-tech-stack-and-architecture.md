# ADR-0001. Стек технологий и архитектура сайта

| Поле | Значение |
|---|---|
| Статус | Принято |
| Дата | 25.10.2026 |
| Автор | Алекс (разработчик); текст подготовлен Claude по обсуждению |
| Связанные документы | [Бизнес-требования](../../../business-requirements/business-requirements.md), прототип v1.3 |

## Контекст

Нужен полноценный самостоятельный сайт каталога «Совпало» вместо прототипа на claude.ai. Исходные условия:

- **Команда.** Владелец формулирует требования, сайт делает один разработчик на JS/TS.
- **Данные.** Notion не используем как источник. База данных есть с первого дня. Первое время карточки брендов загружаются в неё импортом из JSON-файла. Админка появится позже, но архитектура должна её предусматривать.
- **Требования BR, которые влияют на архитектуру:**
  - случайный порядок карточек для каждого посетителя без записи в браузер (FR-2);
  - фильтры, поиск с учётом окончаний и подсветкой (FR-4 — FR-6);
  - прямые адреса `/brands/<id>/` (FR-19);
  - посадочные страницы с включённым фильтром (FR-30);
  - серверный счётчик переходов без cookie и IP (FR-28), по нему считается гарантия 250 переходов;
  - UTM-метки и промокоды в ссылках магазинов (FR-18);
  - никаких зарубежных ресурсов на сайте (NFR-6), хостинг и домен в России (NFR-5);
  - сайт закрыт от поисковиков до открытия (NFR-7).
- **Ответы на уточняющие вопросы (25.10.2026):**
  - личного кабинета бренда нет;
  - в админке работают владелец и разработчик;
  - еженедельные цифры заказов бренды присылают по почте, оператор вносит их вручную;
  - онлайн-оплаты пока нет, но позже она возможна;
  - сайт пока ничего не отправляет: ни писем, ни уведомлений;
  - хостинг — VPS в Selectel, prod и staging;
  - срока первой версии нет.

## Решение

### Схема

```
Браузер ──► nginx ──► Next.js (SSR, TypeScript)
                        ├─ страницы каталога, брендов, «Для брендов», посадочные
                        ├─ /go/<бренд>/<магазин> ── +1 в click_daily ── 302 в магазин
                        └─ сервисный слой (brands, clicks) ──► PostgreSQL (Drizzle)
                                                                  ▲
brands.json ──► CLI import:brands (Zod, upsert) ──────────────────┤
                                                                  │
позже: админка ──► тот же сервисный слой ─────────────────────────┘
```

### 1. Приложение: Next.js + TypeScript

- Next.js (App Router), серверный рендеринг, Node.js 22 LTS. Одно приложение — один деплой.
- Страницы каталога и посадочных рендерятся на сервере при каждом запросе, потому что порядок случайный. Страницы брендов можно кешировать (ISR).
- Клиентский JS минимальный: фильтры работают и без него, через параметры URL. Тот же URL с параметрами — основа посадочных страниц (FR-30), например `/temy/retro` с предустановленным фильтром.

### 2. База данных: PostgreSQL + Drizzle с первого дня

- PostgreSQL 16 — единственный источник данных сайта: бренды, справочники и счётчик переходов.
- ORM — Drizzle, схема описана в TypeScript, миграции — drizzle-kit. Второй ORM (Prisma, TypeORM) не добавляем.
- Основные таблицы:
  - `brands`: id (slug для `/brands/<id>/`), название, город, описание, статус, цена от и до, паспорт (посадка, плотность, состав, размеры, техника, где сделано, тираж), метки «Авторский дизайн» и «Лицензия», цвет, обложка, дата проверки данных, `search_vector`;
  - `brand_shops`: магазин бренда (тип, URL, промокод, нужны ли UTM);
  - справочники `themes`, `styles`, `fits`, `values` и таблицы связей бренда с ними;
  - `click_daily`: счётчик переходов, см. п. 5;
  - `imports`: журнал импортов (когда, файл, сколько добавлено, обновлено, ошибок).
- У бренда есть статус `showcase | hold | reserve` (FR-33). На сайт попадают только `showcase`; скрытые и резервные бренды хранятся в той же базе.
- Страницы не ходят в базу напрямую, только через сервисный слой (`brands`, `clicks`). Его же позже будет использовать админка.

### 3. Загрузка брендов из JSON

- Первое время карточки брендов попадают в базу **только импортом из JSON-файла**. Это консольная команда `pnpm import:brands <файл.json>`, которая запускается локально или на сервере.
- Формат файла описан схемой Zod в коде. Из неё же генерируется JSON Schema, чтобы файл можно было проверять в редакторе.
- Как работает импорт:
  1. Проверяет весь файл по схеме. Если есть хотя бы одна ошибка, в базу ничего не пишется, а команда выводит список ошибок с id бренда и полем.
  2. Делает upsert по id бренда в одной транзакции. Бренд, которого уже нет в файле, не удаляется; по умолчанию его статус меняется на `hold`. Это поведение можно отключить флагом.
  3. Значения справочников (темы, стили) создаются автоматически, если их ещё нет.
  4. Пишет итог в `imports` и выводит отчёт: сколько брендов добавлено, обновлено и скрыто.
- Флаг `--dry-run` проверяет файл и показывает, что изменится, ничего не записывая.
- Импорт идемпотентен: повторный запуск с тем же файлом ничего не меняет.
- Для локальной разработки и staging в репозитории лежит `data/brands.sample.json` с несколькими брендами. Реальный файл в репозиторий не кладём.

### 4. Поиск

- Используем полнотекстовый поиск PostgreSQL. Колонка `brands.search_vector` (`tsvector`, конфигурация `russian`) собирается из названия, описания, тем, стиля, посадки, ткани, города, ценностей и места производства (FR-6). По колонке строится GIN-индекс.
- Окончания учитывает русская морфология PostgreSQL. Совпадения подсвечиваются через `ts_headline`. Порядок найденного случайный.
- Колонка пересчитывается при импорте и при любом изменении бренда через сервисный слой.

### 5. Переходы в магазины

- Кнопка магазина — ссылка на свой домен: `/go/<бренд>/<магазин>?from=<страница или фильтр>&c=<кампания>`.
- Обработчик делает две вещи:
  1. Увеличивает счётчик в таблице `click_daily`: бренд, магазин, день, источник, кампания и счёт; первичный ключ — первые пять полей, запись через `INSERT … ON CONFLICT DO UPDATE`.
  2. Отвечает редиректом 302 на ссылку магазина. К ней добавляются UTM-метки и промокод бренда; к ссылкам на Telegram и VK метки не добавляются (FR-18).
- Отдельные клики, IP, cookie и User-Agent не храним.
- Защита счёта:
  - считаем только GET-запросы с Referer нашего домена и без бот-User-Agent;
  - `/go/` закрыт в `robots.txt`;
  - у ссылок стоит `rel="nofollow"`;
  - используем обычный тег a, а не компонент Link, чтобы предзагрузка Next.js не накручивала счёт.
- IP в логах nginx для `/go/` не пишется.
- Метку кампании из Директа передаём через параметры внутренних ссылок, потому что в браузер ничего не пишем.

### 6. Без зарубежных ресурсов

- Шрифт Onest лежит в репозитории и подключается через `next/font/local`. Google Fonts, внешних CDN, виджетов и счётчиков нет.
- Телеметрия Next.js выключена (`NEXT_TELEMETRY_DISABLED=1`).
- До открытия каталога на всех страницах стоит `noindex`, а `robots.txt` всё запрещает (NFR-7). Управляется переменной окружения.

### 7. Инфраструктура

- VPS в Selectel. Docker Compose: `app` (Next.js), `postgres`, `nginx` с TLS. На одном сервере два стека — `prod` и `staging`.
- Фото брендов (позже, после анкеты) хранятся в S3-хранилище Selectel. Обложки-макеты первой версии лежат в репозитории.
- Бэкап — ежедневный `pg_dump` в S3 Selectel.
- Миграции базы применяются при деплое, до запуска нового контейнера.
- CI/CD: GitHub Actions. Он проверяет типы, линтер, тесты и пример `brands.sample.json` по схеме импорта, затем собирает образ, кладёт его в Container Registry Selectel и деплоит по SSH. Ветка `main` выкатывается на staging, тег — на prod.
- Секреты хранятся в GitHub Actions и в `.env` на сервере, в репозитории их нет.

### 8. Что предусмотрено, но не делается сейчас

| Что | Когда | Как ляжет в архитектуру |
|---|---|---|
| Админка | Позже | Раздел `/admin` в том же приложении, роли admin и editor. Работает через тот же сервисный слой и ту же схему, что и импорт. Каким инструментом её делать (свои страницы или CMS, например Payload), решаем отдельным ADR. Если выберем CMS со своей схемой, понадобится миграция данных |
| Свои формы: анкета, согласие на имя, жалобы | Вместе с админкой | Таблицы в той же базе. До этого — ссылки на Яндекс Формы по BR |
| Онлайн-оплата брендами | Возможно позже | Отдельный модуль `payments` за интерфейсом, российский провайдер. Выбор провайдера — отдельный ADR, после решения о форме приёма денег (NFR-14) |
| Отправка писем | Пока не нужна | SMTP Яндекс 360 через отдельный модуль `mail` |
| Яндекс Метрика | Решение владельца (FR-29) | Подключается только после согласия на cookie |

## Отклонённые варианты

| Вариант | Почему нет |
|---|---|
| Статический сайт (Astro и т. п.) | Нужны свой бэкенд, счётчик переходов, позже админка и формы |
| Django + PostgreSQL | Хорошая встроенная админка, но разработчик пишет на JS/TS |
| Payload CMS сразу | Админка пока не нужна. Payload диктует свою структуру таблиц, а нам нужна своя схема под импорт, поиск и счётчик |
| Бренды в JSON-файле без базы | Нужны поиск PostgreSQL, статусы hold и reserve и будущая админка поверх тех же данных. JSON остаётся только форматом импорта |
| Prisma или TypeORM вместо Drizzle | Тяжелее и медленнее на холодном старте; Drizzle ближе к SQL, что удобно для полнотекстового поиска и upsert счётчика |
| Notion как источник данных | Решение команды; к тому же это зарубежный сервис и в нём нельзя держать персональные данные (NFR-3) |
| Учёт переходов JS-маячком (`sendBeacon`) | Режется блокировщиками, не видит открытие в новой вкладке и копирование ссылки |
| Учёт переходов целями Яндекс Метрики | Нужно согласие на cookie, видна только часть посетителей; для К4 отвергнуто в BR (FR-31) |
| Сторонний сокращатель ссылок | Внешний сервис и передача данных наружу |

## Последствия

**Плюсы**
- Один язык и одно приложение. Один разработчик держит весь стек.
- Счёт переходов серверный, полный и проверяемый. По нему можно считать гарантию и К4.
- Данные с первого дня в базе. Админку, формы и оплату можно добавить без переписывания страниц и без переноса данных.
- Импорт из JSON проверяемый, идемпотентный и с отчётом, поэтому его можно спокойно запускать повторно.
- Инфраструктура — один VPS, около 1–2 тыс. ₽ в месяц **[догадка]**.

**Минусы и риски**
- До появления админки бренды правятся через JSON-файл и повторный импорт. Владельцу без разработчика это неудобно.
- Если правка в базе и повторный импорт старого файла совпадут, импорт перезапишет правку. До появления админки JSON-файл — главный источник, правки делаем в нём.
- Один VPS — единая точка отказа. Для этапа 2 это приемлемо; бэкапы ежедневные.
- GitHub — зарубежный сервис. Он используется только для кода и CI, на сайт не влияет, но доступность из России стоит отслеживать.
